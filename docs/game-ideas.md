# 게임 방향 후보 (T-004)

README의 목표 "Action에서 사용할 게임 만들기"는 뜻이 둘 이상이다. "Action"을 어떻게 읽느냐에 따라 후보를 3개로 나눴다.

## 후보 A. GitHub Actions로 돌아가는 게임: "이슈 던전"
- **한 줄 설명**: 이슈에 댓글로 명령을 쓰면 워크플로가 계산해서 README의 던전 지도를 바꿔 주는 텍스트 게임.
- **플레이**: 이슈에 `/move 북`, `/attack` 같은 댓글을 쓴다. 워크플로가 상태 파일(JSON)을 고치고 README 그림을 갱신한 뒤 댓글로 결과를 알려 준다.
- **기술 스택**: GitHub Actions(이슈 댓글 트리거), Node.js 또는 Python 스크립트, 상태는 저장소 안의 JSON 파일.
- **장점**: 서버·호스팅이 필요 없다. 저장소 자체가 게임판이라 "Action에서 사용"이라는 말에 가장 정확히 맞는다.
- **단점/어려운 점**: 한 턴에 수십 초 걸린다. 동시에 여러 명이 하면 상태 충돌이 난다. 워크플로 권한(쓰기 권한, 봇 커밋) 설정을 이해해야 한다.
- **첫 마일스톤**: 이슈에 `/move` 댓글을 달면 워크플로가 JSON의 좌표를 바꾸고 "현재 위치: (1,0)"이라고 댓글로 답한다.

## 후보 B. 액션 장르 게임: "브라우저 2D 액션"
- **한 줄 설명**: 캐릭터를 움직이고 점프하며 적을 피해 코인을 모으는 2D 액션 게임. GitHub Actions가 자동으로 GitHub Pages에 배포한다.
- **플레이**: 링크를 열고 키보드(방향키+스페이스) 또는 모바일 터치 버튼으로 한다.
- **기술 스택**: TypeScript + Vite, 캔버스는 Phaser 또는 순수 Canvas. 테스트는 Vitest(게임 규칙만). 배포는 GitHub Actions + Pages.
- **장점**: 눈으로 바로 보이고 재미를 느끼기 쉽다. 링크 하나로 누구에게나 공유된다. 로직/화면 레인 분리가 쉽다.
- **단점/어려운 점**: 입력·충돌·애니메이션 등 배울 것이 많다. 그림·소리 에셋이 필요하다. 모바일 조작 최적화가 까다롭다.
- **첫 마일스톤**: 네모 캐릭터가 방향키로 움직이는 빈 화면을 Pages에 자동 배포해서 링크로 열린다.

## 후보 C. 매일 한 판 퍼즐: "Action이 내 주는 일일 퍼즐"
- **한 줄 설명**: 스케줄(cron)로 돌아가는 Action이 매일 새 퍼즐을 만들어 사이트에 올리고, 사람은 브라우저에서 푼다.
- **플레이**: 매일 열리는 웹 페이지에서 단어/숫자 퍼즐 하나를 푼다. 기록은 브라우저에 저장한다.
- **기술 스택**: 정적 HTML + JavaScript, 퍼즐 생성 스크립트(날짜를 씨앗으로 사용), GitHub Actions 스케줄 + Pages.
- **장점**: 서버가 없고 게임 규칙이 작아서 테스트하기 쉽다. "Action으로 운영"과 "직접 할 수 있는 게임"을 둘 다 얻는다.
- **단점/어려운 점**: 퍼즐 품질과 난이도 조절이 어렵다. 매일 새로움을 유지하려면 생성 규칙을 잘 짜야 한다. 액션 장르 느낌은 없다.
- **첫 마일스톤**: 날짜를 넣으면 같은 퍼즐이 항상 나오는 함수를 만들고, 페이지에 오늘의 퍼즐 한 개를 보여 준다.

## 총괄 추천: 후보 B (브라우저 2D 액션 + Pages 자동 배포)
이유:
1. 초보자 첫 게임으로 결과가 눈에 보여서 동기가 유지된다.
2. README 문구를 두 방식으로 모두 만족한다. 액션 장르이고, 배포는 GitHub Actions로 한다.
3. 작게 시작할 수 있다. 네모 하나 움직이기에서 출발해 적, 점수를 조금씩 더하면 된다.
4. 게임 규칙(L1)과 화면(L2)이 자연스럽게 나뉘어 현재 운영 체계의 레인과 잘 맞는다.

후보 A는 가장 가볍고 빨리 끝나서 "연습용 작은 게임"으로 나중에 붙이기 좋다.
